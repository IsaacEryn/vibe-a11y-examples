# 복사해서 쓰는 프롬프트 모음

《바이브 코딩, 접근성까지 부탁해》 본문에 등장하는 프롬프트들입니다.
그대로 복사해 쓰되, `[대괄호]` 부분은 프로젝트에 맞게 바꿔주세요.

## 4장 — 요구사항 한 장 만들기

```text
이런 서비스를 만들려고 해: [아이디어를 한두 문장으로].
아래 형식의 요구사항 문서로 정리해줘. 각 항목마다 내가 결정해야 할 질문이 있으면 물어봐줘.
① 한 문장 정의 ② 주 사용자와 사용 상황 ③ 핵심 과업 1~2개
④ 화면 목록 (최소한으로) ⑤ 이번에 안 만들 것 ⑥ 완성 판정 기준

정리 규칙:
- 내가 답하지 않은 항목은 임의로 채우지 말고 [미정]으로 표시해줘.
- 정리가 끝나면 전체를 한 화면 분량으로 요약하고, 아직 남은 결정을 목록으로 알려줘.
참고: 사용자는 키보드만 사용하는 사람, 화면을 소리로 듣는 사람을 포함한다. 이 전제를 요구사항에 반영해줘.
```

## 4장 — AI에게 배포 시키기

```text
이 프로젝트를 배포하고 싶어. 나는 배포 경험이 없어.
① 이 프로젝트가 정적 사이트인지 서버가 필요한지 판단해줘.
② 무료로 시작할 수 있는 호스팅을 2~3개 비교해서 하나를 추천해줘.
③ 추천한 곳에 배포하는 과정을 단계별로 안내해줘. 명령어가 필요하면 실행 전에 무슨 일을 하는 건지 한 줄씩 설명해줘.
④ 배포 후 내가 직접 확인해야 할 것들의 체크리스트를 만들어줘.
진행 규칙:
- 실제 명령 실행이나 설정 변경은 한 단계씩, 내 확인을 받고 진행해줘.
- 중간에 오류가 나면 내가 오류 메시지를 그대로 붙여줄게. 원인 설명과 해결 단계를 안내해줘.
- 유료 결제가 필요해지는 선택지는 그 시점에 미리 알려줘.
```

## 5장 — 프로젝트 시작 선언

```text
지금부터 이 프로젝트의 모든 UI 작업에 적용할 기준을 알려줄게.
- 목표: 키보드만 사용하는 사용자와 스크린리더 사용자를 포함해 누구나 전 기능을 사용할 수 있는 웹. WCAG 2.2 AA(한국 기준 KWCAG 2.2)를 준수한다.
- 항상 지킬 것: 시맨틱 HTML 우선, 모든 이미지에 alt, 모든 입력 필드에 label, 명도 대비 4.5:1 이상, 색만으로 정보 전달 금지, 포커스 표시 유지.
- UI 코드를 만들 때마다, 적용한 접근성 처리를 코드 아래에 목록으로 보고해줘.
앞으로 내 요청이 이 기준과 충돌하면, 진행하기 전에 그 사실을 알려주고 대안을 제안해줘.
이 기준을 이해했으면 요약해서 확인해줘.
```

## 5장 — 화면 단위 요청 (틀)

```text
[만들 것]을 만들어줘.
사용자 조건:
- 키보드만 사용하는 사용자가 [핵심 동선]을 처음부터 끝까지 완료할 수 있어야 해.
- 스크린리더 사용자가 [핵심 정보]를 이해할 수 있어야 해.
- [이 화면에 특히 중요한 조건 1~2개]
진행 규칙:
- 내가 정하지 않은 결정(문구, 색, 세부 배치)이 필요하면 임의로 정하지 말고 물어봐줘.
- 완성하면 적용한 접근성 처리를 목록으로 보고하고, 위 조건을 스스로 점검한 결과를 함께 알려줘.
```

## 8장 — 접근성 기본 규칙 세트

```markdown
## 접근성 규칙 (모든 UI 작업에 적용)

이 프로젝트의 화면은 키보드만 사용하는 사용자와 스크린리더 사용자가
모든 기능을 사용할 수 있어야 한다. 아래 규칙은 예외 없이 적용한다.

### 구조
- 클릭 요소: 동작 실행은 <button>, 페이지 이동은 <a href>.
  div/span + onclick 금지. role과 tabindex로 흉내 내지 않는다.
- 제목은 <h1>~<h6>를 순서대로. 스타일 때문에 제목 레벨을 건너뛰지 않는다.
- 페이지 구조는 <header> <nav> <main> <footer> 랜드마크를 사용한다.

### 이미지·색
- 모든 <img>에 alt 작성. 정보가 있으면 내용을 설명하고,
  장식이면 alt=""(빈 값)로 둔다. 파일명을 alt에 넣지 않는다.
- 텍스트와 배경의 명도 대비는 4.5:1 이상(큰 텍스트 3:1).
- 색만으로 상태를 구분하지 않는다. 아이콘·텍스트를 병행한다.

### 폼·상호작용
- 모든 입력 필드에 <label>을 연결한다. placeholder로 label을 대신하지 않는다.
- 오류 메시지는 텍스트로 표시하고 해당 필드와 연결한다.
- 모달을 열면 포커스를 모달 안으로 옮기고, 닫으면 원래 위치로 되돌린다.
  ESC로 닫을 수 있게 한다.
- 포커스 표시(outline)를 제거하지 않는다. 디자인 변경은 허용, 삭제는 금지.

### 모바일·모션·문서
- 뷰포트에서 확대를 막지 않는다 (user-scalable=no, maximum-scale 금지).
- 양수 tabindex 금지. 글자 크기는 rem 단위, 본문 1rem(16px) 이상.
- 애니메이션에는 prefers-reduced-motion 대응을 포함한다.
- 문서에 lang="ko"와 페이지를 설명하는 <title>을 지정한다.
- 화면 갱신을 시각으로만 알리지 않는다. 상태 메시지는 role="status"로 함께 알린다.

### 작업 방식
- UI 코드를 생성·수정한 뒤에는 위 규칙 위반 여부를 스스로 점검하고,
  위반이 있으면 수정한 뒤 결과에 점검 내역을 표시한다.
```

## 9장 — 가짜 버튼 일괄 수정

```text
이 프로젝트에서 클릭 이벤트가 달린 `div`와 `span`을 전부 찾아서 시맨틱 요소로 교체해줘.
먼저 대상 목록(파일, 요소, 개수)만 보여주고, 내가 확인하면 한 파일씩 수정해줘.
- 동작을 실행하는 것은 `<button type="button">`으로, 페이지를 이동하는 것은 `<a href>`로 바꿔줘.
- 카드형 UI는 내부 제목을 링크로 만들고 클릭 영역만 카드 전체로 확장해줘.
- `role="button"`이나 `tabindex`, `onkeydown`으로 버튼을 흉내 내는 방식은 사용하지 마.
- 기존 클래스와 스타일은 그대로 유지하고, 필요하면 버튼의 브라우저 기본 스타일(테두리·배경)만 초기화해줘.
- 바꾼 요소 목록과 각각 버튼/링크 중 무엇으로 바꿨는지, 판단 이유를 함께 보여줘.
```

## 9장 — 수정 검증

```text
방금 수정한 파일에서 클릭 가능한 요소를 전부 나열하고, 각 요소에 대해 다음을 표로 정리해줘:
① 사용한 HTML 요소 ② Tab으로 포커스 가능한지 ③ Enter/Space로 동작하는지 ④ 스크린리더에 어떤 역할로 읽히는지.
하나라도 충족하지 못하는 요소가 있으면 그 이유와 수정안을 제시해줘.
```

## 10장 — 이미지 대체 텍스트 전수 점검

```text
이 프로젝트의 모든 `<img>`와 인라인 `<svg>`·아이콘(및 배경이미지로 정보를 전달하는 요소)을 찾아 표로 정리해줘:
① 파일/위치 ② 분류(정보/기능/장식) ③ 현재 alt ④ 제안 alt ⑤ 판단 근거.
규칙:
- 장식 이미지는 alt=""(빈 값)로. alt 속성 생략은 금지.
- 기능 이미지(링크·버튼 안)는 생김새가 아니라 동작/목적지를 설명.
- 파일명, "이미지", "사진" 같은 무의미한 값 금지.
- 이미지 안에 글자가 있으면 그 글자를 alt에 포함하고, 실제 텍스트로 대체할 수 있는지 별도 표시.
- 장식용 svg·아이콘은 aria-hidden="true", 기능용(버튼·링크 안)은 접근 가능한 이름 부여.
확신이 없는 항목은 "사람 확인 필요"로 표시해줘.
표를 먼저 보여주고, 내가 승인한 항목만 일괄 적용해줘. 적용 후 "사람 확인 필요" 목록을 따로 정리해줘.
```

## 11장 — 색 대비 일괄 수정

```text
이 프로젝트의 CSS에서 텍스트/배경 색 조합을 전부 추출해서 표로 만들어줘:
① 사용 위치 ② 전경/배경 색상값 ③ 대비 비율 ④ 기준(본문 4.5:1, 큰 텍스트·UI 요소 3:1) 통과 여부.
미달 조합에는 수정안을 제시하되:
- 색상(hue)은 유지하고 명도만 조정해서 브랜드 색 계열을 지켜줘.
- 그라데이션·이미지 배경 위 텍스트는 가장 불리한 지점 기준으로 판단하고, 필요하면 텍스트 뒤에 반투명 배경층을 제안해줘.
- 색만으로 상태를 구분하는 UI(상태 점, 차트 범례, 오류 표시)를 찾아 아이콘·텍스트·무늬 병행안을 함께 제시해줘.
수정은 가능하면 색상 변수(토큰) 단위로 제안해서 한 번에 반영되게 하고, 적용 전에 영향을 받는 화면 목록을 알려줘.
```

## 12장 — 키보드 접근성 일괄 점검·수정

```text
이 프로젝트에서 다음을 찾아서 고쳐줘:
1. `outline: none` 등 포커스 표시를 제거하는 CSS를 전부 찾아 제거하고, `:focus-visible` 기반의 포커스 링(브랜드 색, 대비 3:1 이상)으로 교체해줘.
2. 양수 tabindex를 전부 찾아서, DOM 순서 조정으로 대체하는 방안을 제시해줘.
3. CSS(order, position)로 시각 순서와 DOM 순서가 어긋난 구간을 찾아 보고해줘.
4. Tab으로 도달할 수 없는 조작 요소, 빠져나올 수 없는 위젯이 있는지 점검해줘.
진행 규칙: 1~4의 발견 사항을 먼저 표로 보고하고, 내가 승인하면 항목별로 수정해줘.
수정 후 각 변경 내역을 파일별로 정리해서 보여줘.
```

## 13장 — 폼 접근성 전수 점검·수정

```text
이 프로젝트의 모든 폼을 찾아 필드별 표로 점검하고 수정해줘:
① 필드 ② label 연결 여부(for/id) ③ placeholder를 label 대신 사용하는지 ④ 필수 표시 방식 ⑤ autocomplete 적용 ⑥ 오류 메시지의 위치·연결(aria-describedby)·내용.
수정 규칙:
- placeholder만 있는 필드는 보이는 label을 추가하고, placeholder는 형식 예시로만 남겨줘.
- 오류 메시지는 필드 곁에 표시하고 aria-describedby로 연결, 제출 시 첫 오류 필드로 포커스 이동, 기존 입력값 보존.
- 필수 표시는 색·별표 단독 금지, required 속성과 텍스트 병행.
- 글자 판독형 CAPTCHA가 있으면 대체 인증 방식을 제안해줘.
폼의 제출·검증 로직은 동작이 바뀌지 않게 유지하고, 바꿔야 한다면 이유를 먼저 설명하고 승인을 받아줘.
변경 전/후 코드를 필드별로 보여줘.
```

## 14장 — 모달 전수 점검·교체

```text
이 프로젝트에서 모달·팝업·오버레이 구현을 전부 찾아 점검하고 수정해줘.
- 우선 네이티브 `<dialog>` + `showModal()`로 교체 가능한 것은 교체해줘. 기존 디자인은 유지.
- 교체가 어려운 것은 다음 체크리스트로 점검·보완해줘: 열릴 때 포커스 인, Tab/Shift+Tab 순환, ESC 닫기, 닫힐 때 포커스 복귀, role="dialog"·aria-modal·aria-labelledby, 배경 inert 처리.
- 닫기 버튼에 접근 가능한 이름("닫기")이 있는지 확인해줘.
- 교체 전에 모달 목록과 교체/보완 구분안을 먼저 보여주고, 내가 승인하면 하나씩 진행해줘.
- 모달별 점검 결과를 체크리스트 표로 보고해줘.
```

## 15장 — 모바일 접근성 일괄 점검·수정

```text
이 프로젝트를 모바일 접근성 관점에서 점검하고 수정해줘:
1. 뷰포트 메타태그에서 user-scalable=no, maximum-scale 제한을 찾아 제거해줘.
2. 화면 방향을 고정하는 설정·CSS·스크립트가 있으면 보고하고 제거를 제안해줘.
3. 드래그·스와이프·길게 누르기·흔들기로만 조작되는 기능을 전부 나열하고, 각각에 단순 탭 대체 수단을 추가해줘.
4. 호버에만 의존해 표시되는 콘텐츠(툴팁, 드롭다운, 버튼)를 찾아 터치·포커스로도 접근 가능하게 바꿔줘.
5. 터치 대상이 44×44px 미만이거나 간격이 부족한 곳을 보고해줘.
각 수정이 데스크톱 화면에 영향을 주는지 함께 확인하고, 영향이 있으면 적용 전에 알려줘.
항목별 변경 내역을 표로 정리해줘.
```

## 16장 — 접근성 현황 진단과 수리 계획

```text
이 프로젝트 전체를 접근성 관점에서 진단하고 수리 계획을 세워줘.
1. 3부 유형별로 문제를 찾아줘: 가짜 버튼, 무의미한 alt, 색 대비, 키보드(포커스 표시·순서·함정), 폼(label·오류), 모달, 모바일(뷰포트·제스처).
2. 각 문제에 다음을 표기해줘: 위치 / 공통 컴포넌트 여부 / 심각도(차단·불편·미관) / 핵심 동선(가입·결제 등) 해당 여부.
3. "핵심 동선 × 공통 컴포넌트 × 차단"이 겹치는 것부터 정렬한 수리 계획을 만들어줘. 한 번에 한 컴포넌트씩, 각 단계의 예상 변경 범위를 함께.

지금은 진단과 계획만. 수정은 내가 승인한 뒤 단계별로 진행하자.
```

## 20장 — 검사 대상 목록 만들기

```text
이 프로젝트의 라우트(페이지) 구조를 분석해서 접근성 검사 대상 목록을 만들어줘.
1. 페이지를 템플릿 유형별로 분류해줘.
2. 다음 다섯 그룹으로 대표 표본을 제안해줘: 공통 페이지 / 핵심 과업 전 과정(과업을 지정해줄게: [핵심 과업]) / 유형별 대표(콘텐츠가 복잡한 개체 기준) / 상태·변형(로그인 전후, 빈/오류 상태, 모바일) / 무작위 2~3개.
3. 표로 정리해줘: 유형 / URL / 검사할 상태 / 비고.
4. 표본에서 빠진 페이지가 없는지 전체 라우트 목록과 대조한 결과를 함께 보여줘.
```

## 21장 — 접근성 검사 자동화 설정

```text
이 프로젝트에 자동 접근성 검사를 설정해줘.
시작 전에 우리 스택에 맞는 검사 도구 선택지를 2개 비교하고, 추천과 이유를 먼저 알려줘.
1. axe 기반 검사를 다음 페이지들에 대해 실행하는 테스트를 만들어줘: [20장의 검사 대상 목록]
2. 배포 전에 이 테스트가 자동 실행되고, 새로운 위반이 발견되면 배포가 중단되게 해줘.
3. 기존 위반은 기준선(baseline)으로 기록해두고, 기준선보다 늘어나는 것만 실패로 처리해줘.
4. 검사 결과가 위반별로 어떤 페이지·요소에서 나왔는지 보고서로 남게 해줘.
설정 후, 일부러 위반(alt 없는 img)을 하나 넣어 검사가 실제로 실패하는지 확인해줘.
```

## 24장 — 실습: 랜딩 페이지 생성

```text
원데이 클래스 모집 랜딩 페이지를 만들어줘. 정적 HTML + CSS 한 파일로.
내용: 클래스 소개(제목·설명·강사), 일정과 장소, 신청 폼(이름·연락처·희망 날짜 선택·문의 사항).
사용자 조건:
- 키보드만 사용하는 사용자가 페이지 진입부터 신청 완료까지 막힘 없이 갈 수 있어야 해.
- 스크린리더 사용자가 클래스의 핵심 정보(무엇을·언제·어디서·얼마에)를 순서대로 들을 수 있어야 해.
- 6장의 시각 원칙: 본문 16px 이상, 명도 대비 4.5:1 이상, 터치 대상 44px.
코드는 파일 하나로, 외부 라이브러리 없이 만들어줘.
완성하면 적용한 접근성 처리 목록과 함께, Tab 이동 순서와 제목 구조(h1~h3)도 보고해줘.
```
